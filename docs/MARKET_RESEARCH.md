# AskMe 市场调研与需求深挖

日期：2026-06-05

状态：第二版公开资料调研 + 仓库产品能力映射。结论用于指导需求访谈、产品聚焦和路线排序，不等同于客户已验证需求；产品需求主干见 `docs/PRODUCT_REQUIREMENTS.md`，需求证据台账见 `docs/DEMAND_EVIDENCE_LEDGER.md`，场景 ROI 模型见 `docs/SCENARIO_ROI_MODEL.md`，定价包装假设见 `docs/PRICING_PACKAGING_HYPOTHESES.md`。

## 一句话结论

AskMe 不应被定义为“机器人聊天工具”或“机器人底盘控制系统”。更准确的市场是：

> 面向园区、厂区、仓储、景区等现场服务场景的机器人运营交付中台，把自然语言、现场事件、知识证据、客户项目、对象目录、技能包、运行时交接和验收审计连成可交付闭环。

短期最有机会的客户不是终端大客户的一线用户，而是机器人方案商、集成商、试点交付团队和有多站点运维压力的安防/物业/工业现场运营方。

## 市场边界

### 采用替代原则后的市场定义

客户实际替代的不是一个“聊天框”，而是以下现有做法：

| 客户当前选择 | 是否是 AskMe 的直接替代 | 原因 |
| --- | --- | --- |
| 人工安保/保洁/巡检 + 微信/电话/Excel | 是，预算来源相近 | 客户买的是响应、记录、闭环和责任，而不是单纯买机器人。 |
| 机器人 OEM 自带 fleet/app/遥控平台 | 部分是 | OEM 平台通常强在硬件、导航、遥控和任务执行，弱在跨客户项目、知识、验收、证据和多角色运营。 |
| 视频监控/VMS + AI 告警 | 部分是 | 可以发现异常，但通常不能把语音交互、移动机器人任务、人员通知和验收证据串成闭环。 |
| CMMS/工单/物业管理系统 | 邻近替代 | 管工单强，但对移动机器人、现场感知、语音交互和客户演示弱。 |
| 定制项目脚本/一次性 Demo | 是 | 这是 AskMe 最该替代的交付模式：难复制、难验收、难维护。 |
| 通用 LLM Agent 平台 | 不是直接替代 | 缺少现场对象、安全预检、运行时 profile、审计和硬件交接边界。 |
| 机器人底盘/运动控制/VLA 控制 | 不属于同一市场 | AskMe 的边界是任务理解、交接和治理，不直接控制电机、步态、串口或 `cmd_vel`。 |

### 市场包含

- 场景机器人交互与任务编排。
- 现场事件运营和闭环管理。
- 客户项目配置、对象目录、行业模板和交付包。
- 知识库/RAG 的客户证据治理。
- 运行时 handoff、安全预检和人工审批边界。
- 验收材料、审计报告、上线准入差距清单。

### 市场排除

- 机器人本体制造。
- 底盘导航、避障、运动控制和机械臂控制。
- 纯 VMS/摄像头算法。
- 纯 CMMS/物业工单。
- 纯通用客服机器人。
- 无现场责任边界的通用 Agent 平台。

## 外部市场信号

### 1. 专业服务机器人仍在增长，但行业很碎

IFR《World Robotics 2025 - Service Robots》显示，2024 年全球专业服务机器人销量增长约 9%，登记销量超过 199,000 台；服务机器人生产商高度分散，IFR 统计到 944 家生产商，且大量是中小企业。RaaS 机队规模增长约 31% 至超过 24,500 台。

对 AskMe 的含义：

- 行业增长不是问题，问题是部署碎、场景碎、交付碎。
- 中小机器人厂商和集成商需要降低每个项目的定制成本。
- RaaS 增长意味着客户更在意持续运营、SLA、报告和可追责，而不只是一次性卖硬件。

### 2. 设施管理/FM 正在从后勤成本项变成运营韧性问题

JLL 2025 全球设施管理报告把 FM 描述为约 3 万亿美元规模的行业，并指出成本效率、业务韧性、员工/访客体验和 AI/自动化 adoption 都在变成关键议题；报告样本中 84% 的 FM 领导者把运营成本和预算约束列为首要关切，28% 已把 AI 嵌入 FM 运营，更多企业处于试点或计划阶段。

对 AskMe 的含义：

- 买方语言应是“降交付/运营成本、提升响应一致性、沉淀证据和验收”，而不是“AI 很聪明”。
- 如果 AskMe 只做语音聊天，会错过预算入口；如果做成现场运营闭环，才能进入 FM/安防/物业预算。

### 3. 安保与保洁岗位有大量替换性需求，但不是简单裁员逻辑

BLS 2024-2034 预测显示，美国 security guards/gambling surveillance officers 每年平均约 162,300 个岗位空缺，janitors/building cleaners 每年平均约 351,300 个岗位空缺，主要由离职、转岗和退休造成。

对 AskMe 的含义：

- 需求不一定来自“减少所有人”，而来自夜间、重复、危险、低频但必须留痕的工作。
- 客户需要机器人和人协同：机器人发现、记录、播报、通知；人复核、处置、签收。
- 人机协同和人工审批不是弱点，而是进入生产现场的信任机制。

### 4. 国内政策方向强调场景落地、试验验证和供需对接

中国《“机器人+”应用行动实施方案》提出到 2025 年推动服务机器人、特种机器人应用深度和广度提升，聚焦制造业、商贸物流、商业社区服务、安全应急和极限环境等重点领域，推广典型应用场景，并建设应用体验和试验验证中心。

对 AskMe 的含义：

- 产品定位应贴近“场景应用、试验验证、可复制方案”，而不是单点算法。
- 客户项目、对象目录、模板、验收 dossier 和现场证据会成为差异化能力。

### 5. 竞品/邻近玩家已经强调“自治 + 人在回路 + 报告”

公开资料显示：

- Cobalt Robotics 把安全机器人定位为企业室内巡逻、AI 检测、human-in-the-loop、数据报告和平台集成。
- Boston Dynamics Spot 的 GraphNav/API 生态面向工业/商业数据采集和巡检，客户常在其 API 上构建初始化、监控和功能层。
- ANYbotics 的 ANYmal 强调工业级 autonomous inspection、数据洞察、现有运营系统集成和安全设计。

对 AskMe 的含义：

- “机器人能动”已经是硬件/OEM 叙事；AskMe 要避开正面竞争。
- AskMe 的差异点应是跨机器人/跨客户项目的交付治理层：项目模板、任务口径、证据、审批、上线准入和运行时边界。

## 本轮需求深挖结论

### 优先 ICP 排序

| 优先级 | 客户分群 | 为什么现在值得优先 | 主要阻力 | AskMe 应卖的第一价值 |
| --- | --- | --- | --- | --- |
| P0 | 机器人方案商 / 集成商 / 交付团队 | 直接承受 Demo 到试点、试点到验收的交付成本；已有客户和机器人；愿意为复制交付、验收包和项目复用买单。 | 客户访谈证据不足；需要证明不会替代 OEM 平台。 | “把一次性机器人 Demo 变成可复制、可验收的客户项目交付包。” |
| P1 | 安保 / 物业 / FM 服务商 | 多项目、多甲方、人员流动和夜班巡逻压力明确；服务报告和责任链有预算入口。 | 采购可能被甲方预算牵引；真实现场设备接入要求高。 | “机器人 + 人工复核 + 证据报告，提升服务透明度和一致性。” |
| P1 | 厂区 / 仓储 / 物流运营方 | 安全、停线、巡检和事件闭环价值高；已有 VMS、传感器、工单系统可接入。 | 销售周期长，上线门槛高，必须有硬件、IAM、审计和安全验收。 | “把现场异常、机器人任务 handoff 和验收证据串成受控闭环。” |
| P2 | 园区 / 商业综合体 / 景区运营方 | 演示友好，问路、导览、异常上报容易理解。 | ROI 容易停留在展示价值，预算刚性弱于安防/FM/工业。 | “可演示、可试点、可验收的场景包。” |
| P3 | 机器人 OEM | 能带来生态入口和渠道协同。 | 平台主导权冲突强，OEM 往往更愿意自建 fleet/app。 | “不抢硬件平台，只补上层场景运营插件。” |

短期主线应先压到 P0：机器人方案商/集成商交付中台。它最贴近 AskMe 现有的客户项目、对象目录、模板、现场事件、证据、审计、验收包和 runtime profile 能力，也最能解释为什么 AskMe 不是聊天机器人。

### 需求强度分层

| 层级 | 需求 | 购买触发 | 当前 AskMe 匹配度 | 需要补的产品化证据 |
| --- | --- | --- | --- | --- |
| Must-have | 客户项目与对象目录 | 每个客户现场点位、设备、路线、事件规则不同，不能靠改代码复制。 | 高 | 项目模板、导入导出、缺口检查、跨客户隔离证明。 |
| Must-have | 试点验收包 / acceptance dossier | 客户要求知道“做了什么、证据在哪、哪些还不能上线”。 | 高 | 可下载交付包、验收用例覆盖、客户签收不等于生产上线的边界说明。 |
| Must-have | 现场事件闭环 | 现场异常不能只停留在告警，需要通知、处理、复核、关闭和报告。 | 高 | 事件时间线、责任人、证据包、关闭审批、客户可读报告。 |
| Must-have | 运行安全边界 | 机器人听懂人但不能乱动，尤其是游客、旁人和高风险任务。 | 高 | InteractionGate、SafetyPreflight、runtime profile、人工确认的客户可读解释。 |
| Must-have | 知识证据治理 | 园区规则、SOP、设备知识不能编造或越权暴露。 | 中高 | 已审批知识、过期/冲突阻断、引用证据、客户/项目可见范围。 |
| Should-have | 外部系统连接清单 | 真实客户已有 VMS、CMMS、IAM、通知、地图、机器人 fleet。 | 中 | 每类系统的最小适配合同、必需字段、失败兜底。 |
| Should-have | 方案商交付仪表盘 | 方案商需要跨项目看试点进度、验收阻断和可复制模板。 | 中高 | 按角色拆 Dashboard，而不是一个页面塞所有功能。 |
| Could-have | 技能包市场 / skill growth | 重复需求需要沉淀成可审批、可灰度、可回滚能力。 | 中 | 从需求到技能草稿、审批、项目级启停、调用审计的闭环。 |
| Later | 多机器人调度和 fleet 优化 | 只有在客户已完成单项目交付后才会强需求。 | 低中 | 需要真实机器人队列、地图、任务冲突和运维数据。 |
| Exclude now | 底盘控制、VLA 运动控制、完全无人值守承诺 | 容易扩大责任边界，且不是 AskMe 当前替代市场。 | 不应做 | 明确留给 Runtime / Safety / Hardware 和 OEM 平台。 |

### 关键购买触发

1. Demo 已经能演示，但客户问“怎么验收、怎么复制到下一个现场”时答不上来。
2. 客户要求交付验收材料、权限审计、现场证据、风险说明和上线准入清单。
3. 一个方案商同时交付多个园区、厂区、仓储或景区项目，项目资料和脚本开始失控。
4. 现场运营方已经有摄像头、传感器、人工巡检或工单系统，但事件闭环和机器人任务交接割裂。
5. 安保、保洁、巡检岗位存在夜班、重复路线、人员流动和服务质量不一致问题。
6. OEM fleet/app 能管机器人，但不能很好回答客户项目、知识证据、签收、审计和跨系统闭环。

### 需求验证指标

访谈时不要只问“需不需要机器人 AI”，要拿以下指标逼近真实需求强度：

| 指标 | 为什么重要 | 目标取证方式 |
| --- | --- | --- |
| Demo 到试点耗时 | 衡量复制交付痛点是否真实。 | 让交付 PM 复盘最近 3 个项目的时间线。 |
| 每个项目人工补材料小时数 | 直接对应 AskMe 的验收包价值。 | 询问验收文档、截图、日志、报告分别由谁补。 |
| 试点卡住原因 Top 5 | 决定产品优先补哪个闭环。 | 让销售/交付分别列损单或延期原因。 |
| 当前系统替代物 | 判断预算从哪里来。 | 记录 VMS、CMMS、Excel、微信群、OEM app、定制脚本现状。 |
| 必须集成系统 | 判断 MVP 是否能上线。 | 逐项确认 IAM、通知、地图、机器人 fleet、工单、审计存档。 |
| 现场事件月频次和关闭责任 | 判断事件闭环是否是刚需。 | 收集安保/保洁/巡检/设备异常的真实台账样例。 |
| 客户愿意付费对象 | 判断定价模型。 | 在项目费、站点费、机器人数量、技能包、交付包、RaaS 运营费中做 forced choice。 |

### 定价假设

先把定价当作访谈假设，不要过早写死。详细包装和架构边界见 `docs/PRICING_PACKAGING_HYPOTHESES.md`：

| 假设 | 适用客户 | 需要验证的问题 |
| --- | --- | --- |
| 按客户项目 / 站点收基础费 | 方案商、FM 服务商、多园区运营方 | 一个项目节省多少交付时间，客户是否接受每站点续费。 |
| 按机器人数量加收运行管理费 | 已有机器人机队的服务商或 OEM 渠道 | 客户是否认为 AskMe 的价值随机器人数量增长。 |
| 按交付验收包一次性收费 | 方案商和交付团队 | 是否能作为 Demo-to-pilot 的项目成本进入预算。 |
| 按行业模板 / 技能包收费 | 有多行业复用需求的方案商 | 客户是否愿意为可复用模板和审批技能包付费。 |
| RaaS 运营报告加成 | 安保/FM 服务商 | 甲方是否愿意为透明报告、SLA 证据和审计留痕付费。 |

### 需求风险

- 如果 P0 方案商不愿意为交付工具付费，AskMe 需要转向 P1 的安保/FM 服务报告和现场事件闭环。
- 如果客户把价值全部归给硬件/OEM fleet，AskMe 必须更强调跨项目证据、验收和多系统运营，而不是机器人控制。
- 如果现场系统集成成本过高，MVP 应先限定 2-3 类输入：人工触发、模拟机器人事件、VMS/传感器 webhook。
- 如果客户只要演示效果，不能证明验收和责任链价值，短期容易变成一次性项目，不适合做平台。
- 如果继续把话术放在“智能聊天”，会错过预算入口并放大安全责任。

## 客户分群

### Segment A：机器人方案商 / 集成商 / 交付团队

一句话画像：有机器人、有客户、有 Demo，但每个项目都靠人肉改配置、写脚本、补材料。

核心需求：

- 快速从 Demo 复制到试点项目。
- 用模板创建客户项目、对象目录、通知组、验收用例。
- 用客户可读 dashboard 和报告证明“这次试点做了什么、缺什么、为什么还不能生产上线”。
- 不想被某个 OEM 平台锁死。

购买触发：

- 一个方案商同时做多个园区/厂区/仓储项目。
- 客户要求提供验收包、现场运行证据、权限审计和上线风险说明。
- Demo 后进入试点，发现原型不能直接交付。

AskMe 产品机会：

- 作为“交付操作系统”卖给方案商。
- 先解决复制交付和验收材料，而不是先追求全自动真实机器人控制。

### Segment B：园区/商业综合体/景区运营方

一句话画像：场景复杂、服务点多、访客问题多、安保/保洁响应依赖人。

核心需求：

- 游客问路、服务点引导、异常上报、夜间巡查。
- 管理员能看到事件闭环、人员响应、证据和日报。
- 不希望游客随口一句话触发机器人执行高风险动作。

购买触发：

- 新园区/景区希望做智能化展示。
- 夜间安保、卫生、停车、人流等问题频繁。
- 管理层希望用机器人和 AI 做服务升级，但现场主管担心误触发和责任。

AskMe 产品机会：

- 先做“可演示 + 可试点 + 可验收”的场景包：问路、异常上报、通知、报告。
- 强调交互准入门、知识证据和人工确认。

### Segment C：厂区 / 仓储 / 物流运营方

一句话画像：更重视安全、设备状态、通道、区域规则和作业中断成本。

核心需求：

- 设备巡检、烟火/温度/通道阻塞/人员闯入。
- 与传感器、摄像头、WMS/MES/CMMS、工单系统对接。
- 需要审计、复盘、SOP 和责任边界。

购买触发：

- 设备巡检和夜间巡查成本高。
- 事故、停线、误报或漏报带来明显损失。
- 已有摄像头/传感器，但事件闭环和机器人联动弱。

AskMe 产品机会：

- 以“现场事件运营 + 机器人任务 handoff + 验收证据”切入。
- 这类客户对生产上线要求高，应把 lab/prod runtime profile、现场验收和人工复核作为卖点。

### Segment D：安保/物业/FM 服务商

一句话画像：按服务合同交付结果，痛点是人员流动、服务一致性和客户投诉。

核心需求：

- 夜间巡逻、到岗证明、异常留痕、响应时效。
- 服务报告能发给甲方。
- 机器人不是替代所有保安，而是让人少跑低价值重复路线。

购买触发：

- 多项目、多甲方，需要标准化服务质量。
- 招人难、人员稳定性低、夜班管理难。
- 甲方要求更高透明度和数字化记录。

AskMe 产品机会：

- 面向服务商提供多客户项目和审计报告。
- 把“机器人 + 人工复核”的责任链做清楚。

### Segment E：机器人 OEM

一句话画像：有机器人和 SDK，但客户现场运营层常常要靠合作伙伴补。

核心需求：

- 快速把机器人接进客户场景。
- 形成行业模板和生态能力。
- 不希望上层系统抢走硬件平台主导权。

购买触发：

- OEM 需要让渠道/集成商更快交付。
- 客户提出知识问答、事件报告、审计和多系统集成需求。

AskMe 产品机会：

- 作为 OEM 的上层场景运营插件，而不是替代 OEM fleet/app。
- 商务上难度较高，因为 OEM 往往希望自己掌握平台入口。

## 深度需求假设

### JTBD 1：把机器人 Demo 变成可验收试点

当方案商拿着机器人和客户完成演示后，需要在不重写代码的情况下创建客户项目、导入点位/对象、配置技能包、生成试点验收用例和交付包，以便客户相信“这不是一次性 Demo”。

产品信号：

- 客户项目、行业模板、对象目录、导入导出。
- Proposal bundle、acceptance dossier、customer signoff。
- 交付差距清单和现场验证 evidence。

### JTBD 2：把现场异常变成闭环事件，而不是一条告警

当摄像头、传感器、机器人或人工发现异常时，现场主管需要知道事件类型、地点、证据、通知对象、处理状态和关闭责任，以便复盘和对客户/管理层交代。

产品信号：

- Field Events、evidence、notification、close/request-close、report。
- 事件时间线、响应组、证据包、审计导出。

### JTBD 3：让机器人听懂人，但不能乱动

当游客、安保或管理员跟机器人说话时，系统需要先判断是否应该回应、是否需要澄清、是否有权限、是否要二次确认、是否可进入运行时 handoff，以避免误触发真实硬件。

产品信号：

- Interaction Gate。
- SafetyPreflight。
- runtime profile：fake/sim/shadow/lab/prod。
- 管理员确认、风险确认、操作员审计。

### JTBD 4：让知识回答可控、可解释、可治理

当客户问园区规则、点位、SOP、设备信息时，运营人员需要让回答来自已审批知识，并能展示依据；过期、冲突、内部、未审批内容不能进入客户回答。

产品信号：

- KnowledgeCatalog、quality_status、visibility、evidence。
- 审批、发布、版本、冲突、过期、回滚。

### JTBD 5：把重复需求沉淀成可审批技能包

当同一类现场需求反复出现时，产品经理需要把它从一次性处理变成可复用技能，但必须先校验、审批、绑定客户项目、灰度发布和审计。

产品信号：

- Skill growth backlog。
- Generated skill draft。
- Skill package release/rollback。
- 客户项目级启停和调用审计。

## 需求优先级判断

### 现在最应该聚焦

1. 方案商/交付团队的复制交付：客户项目、对象目录、模板、导入导出、验收包。
2. 现场事件闭环：事件、通知、证据、关闭、报告。
3. 运行安全边界：交互准入、安全预检、runtime profile、人工复核。
4. 客户可见可信度：知识证据、审计导出、上线准入差距。
5. Dashboard 信息架构：客户负责人、现场主管、交付工程师各看各的东西。

### 暂时不该优先押注

1. 宣称完全无人值守生产上线。
2. 直接做底盘控制或 VLA 运动控制。
3. 追逐通用聊天能力。
4. 做过宽的行业模板市场。
5. 把所有功能塞进一个 Dashboard 页面。

## 当前 AskMe 与市场需求的匹配

已匹配较好：

- 产品边界清楚：大模型不直接控制硬件。
- 已有语音/文本交互、交互准入、知识证据、任务 handoff、现场事件、审计、客户项目和技能包基础。
- 最新整理已经在收紧“生产上线/客户签收/现场验收”的表达，避免销售和交付过度承诺。

主要缺口：

- 缺少真实客户访谈证据：目前需求多来自产品推演和二手资料；所有访谈、试点、artifact 和 quote 必须进入 `docs/DEMAND_EVIDENCE_LEDGER.md` 后才能升级为 validated claim。
- 缺少面向方案商的清晰包装：应该把“复制交付”和“验收材料”做成第一价值主张。
- 缺少已验证 ROI 证据：园区、厂区、仓储、景区的买点不同；当前场景 ROI 模型见 `docs/SCENARIO_ROI_MODEL.md`。
- 缺少关键外部系统连接清单：VMS、CMMS、IAM、地图、机器人 fleet、通知系统、SIEM/WORM；最小字段合同见 `docs/EXTERNAL_SYSTEM_INTEGRATION_CONTRACTS.md`。
- 缺少上线前的硬件/现场验收 checklist 产品化表达；准入清单见 `docs/SITE_LAUNCH_READINESS_CHECKLIST.md`。
- 缺少已验证定价证据：按客户项目、站点、机器人数量、技能包、RaaS 运营费还是交付包收费，需要访谈验证；当前假设见 `docs/PRICING_PACKAGING_HYPOTHESES.md`。

## 访谈计划

目标：验证谁最痛、为什么现在买、用什么预算买、买 AskMe 替代什么、上线前最怕什么。

样本建议：20-30 人。

| 角色 | 数量 | 要验证的问题 |
| --- | --- | --- |
| 机器人方案商/集成商负责人 | 6-8 | 每个项目定制成本、验收材料、客户最常卡点、愿意为交付中台付费吗。 |
| 交付工程师/实施 PM | 5-6 | 项目从 Demo 到试点最耗时的环节、现场配置资料、故障复盘、交接文档。 |
| 园区/景区/商业综合体现场主管 | 4-5 | 每天高频异常、谁处理、如何留痕、机器人服务最担心什么。 |
| 厂区/仓储运维/安全负责人 | 4-5 | 传感器/摄像头/工单系统现状、停线/事故成本、上线审批要求。 |
| 安保/物业/FM 服务商 | 3-4 | 人员流动、夜班巡逻、甲方报告、机器人服务合同怎么定价。 |
| 机器人 OEM 渠道/生态负责人 | 2-3 | 是否愿意开放 SDK/fleet 接口、是否需要上层运营插件。 |

核心问题：

1. 最近一次机器人/AI 现场项目从 Demo 到试点卡在哪里？
2. 客户要求哪些验收材料？哪些材料现在靠人工补？
3. 现场每天最常见的 5 类事件是什么？谁负责关闭？
4. 什么情况会让你拒绝机器人进入生产现场？
5. 你现在用什么系统记录事件、通知、工单和证据？
6. 如果 AskMe 只能先解决一个问题，你愿意付费解决哪个？
7. 你会按项目、站点、机器人数量、技能包还是服务费付费？
8. 哪些系统必须集成才可能上线？
9. 你最怕销售/产品承诺过头的地方是什么？
10. 一个试点成功的量化标准是什么？
